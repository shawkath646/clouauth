# Security & Code Audit Report

**Project:** clouauth (clouburstlab Identity Provider)  
**Audit Date:** 2026-09-01 (Updated 2026-09-11)  
**Framework:** Next.js 16.3.4 (App Router, React 19.2.8, Prisma 7.10.0, Node.js)  
**Overall Risk:** High (Reduced from Critical following initial remediation)  

---

## Executive Summary

A comprehensive, end-to-end security, architecture, authentication, and code quality audit was performed on the `clouauth` codebase. `clouauth` is designed as a centralized OpenID Connect (OIDC) and OAuth 2.0 Identity Provider (IdP) supporting username/password authentication, WebAuthn/passkeys, Time-based One-Time Password (TOTP) 2FA, social logins (Google One Tap, GitHub, Microsoft), and third-party OAuth 2.0 client application registrations.

Following the initial audit, **16 critical, high, medium, low, and informational findings were remediated**:
- Next.js dependencies were upgraded to `16.3.4`, resolving unauthenticated Windows RCE (`GHSA-p293-qw3h-jr36`) and image optimization RCE (`GHSA-2xp9-vwfh-vxw4`).
- `getSession()` was fixed to eliminate arbitrary session revocation and denial-of-service on token hash mismatch.
- `signOutAll(userId)` server action was secured with strict session authentication and user ID authorization.
- `UserEmail.address` unique constraint was added to schema, with duplicate checks in `signUp`, and pre-account takeover via unverified email linking was blocked across OAuth and Google One Tap.
- Stored XSS and arbitrary file uploads via SVG were eliminated by rejecting SVG files and enforcing binary magic byte verification (JPEG, PNG, WebP) on avatar and app icon uploads.
- Session revocation was implemented in `updatePasswordAction` so all other active user sessions are invalidated upon password change.
- Strict Content-Security-Policy (CSP) and HTTP Strict Transport Security (HSTS) response headers were configured in `next.config.ts`.
- GitHub OAuth provider was updated to require `e.primary && e.verified`.
- OIDC Userinfo endpoint was updated to dynamically reflect actual email verification status from the database.
- Connected third-party OAuth access and refresh tokens are now symmetrically encrypted using AES-256-GCM prior to database persistence.
- A strong, unified password policy (minimum 8 characters with uppercase, lowercase, digit, and special characters) was enforced across signup schemas and locale files.
- Constant-time string comparisons (`crypto.timingSafeEqual`) were implemented for session lookup and token rotation.
- Account deletion was implemented end-to-end with transaction cleanup and session cookie invalidation in the Danger Zone UI.
- React `cache()` request deduplication was applied to `getFullProfile()` to eliminate redundant N+1 queries.
- OIDC discovery discrepancy was resolved in documentation (`GET /signin`).
- ESLint errors, type suppressions, and `any` types were cleaned up, achieving 0 errors and 0 warnings.

**13 remaining findings** require user review and subsequent remediation before production deployment, detailed below.

## Critical Findings

### [CRITICAL] Broken OAuth 2.0 Authorization Flow: Missing Client & Redirect URI Validation, PKCE Bypass, and Reusable Authorization Codes
**Confidence:** CONFIRMED  
**Category:** OAuth 2.0 / Open Redirect / Token Hijacking  
**Affected files:** `src/actions/oauth/oauth.actions.ts`, `src/app/api/sso/v1/token/route.ts`  
**Affected routes/functions:** `grantOAuthAccess`, `POST /api/sso/v1/token`  

**Problem**  
1. In `src/actions/oauth/oauth.actions.ts`, `grantOAuthAccess` takes `client_id` and `redirect_uri` directly from client parameters without querying `prisma.oAuthClientConfig`. It never validates whether the `client_id` exists, whether the client is enabled, whether `redirect_uri` matches registered redirect URIs, or whether PKCE is required.
2. In `src/app/api/sso/v1/token/route.ts`, lines 83–107 check `if (codeChallenge) { ... }`. If an attacker omits `code_challenge` during the authorization step, the server completely skips PKCE validation even if `clientApp.pkce_required` is `true`.
3. Authorization codes are stateless signed JWTs with a 5-minute lifespan. The token endpoint does not track whether an authorization code has already been exchanged (no JTI revocation / database tracking), violating RFC 6749 Section 4.1.2 which requires authorization codes to be strictly single-use.

**Attack Scenario**  
An attacker tricks an authenticated user into visiting a malicious link or invokes `grantOAuthAccess("client_123", "https://attacker.com/steal")`. The Server Action signs an authorization code JWT for the victim and redirects to `https://attacker.com/steal?code=...`. The attacker intercepts the code and exchanges it for user access and ID tokens. Because PKCE is skipped when omitted, public clients offer zero protection. Furthermore, intercepted codes can be replayed repeatedly during their 5-minute validity.

**Impact**  
Complete OAuth account takeover, credential theft, and unauthorized access to third-party integrations.

**Recommended Fix**  
1. In `grantOAuthAccess`, look up `prisma.oAuthClientConfig.findUnique({ where: { client_id } })`. Verify `clientApp.enabled`, verify `redirect_uri` is strictly present in `JSON.parse(clientApp.redirect_uris)`, and require `code_challenge` if `clientApp.pkce_required` is `true`.
2. In `POST /api/sso/v1/token`, track exchanged authorization codes (e.g. via `prisma.revokedToken` or a dedicated single-use code table) and reject any code presented more than once.

**Priority:** Immediate

## High Severity Findings

### [HIGH] Information Disclosure: `previous_refresh_token_hash` Leaked via API
**Confidence:** CONFIRMED  
**Category:** Sensitive Data Exposure / Type Assertion Bypass  
**Affected files:** `src/lib/session.ts`, `src/app/api/auth/v1/session/route.ts`  
**Affected routes/functions:** `sanitizeSession`, `GET /api/auth/v1/session`  

**Problem**  
In `src/types/session.types.ts`, `SafeDBUserSession` is declared as:
```ts
export type SafeDBUserSession = Omit<DBUserSession, 'session_token_hash' | 'refresh_token_hash' | 'previous_refresh_token_hash'>;
```
If sanitization only destructures two fields without explicitly omitting `previous_refresh_token_hash`, the cryptographic hash remains present on the object and calling `GET /api/auth/v1/session` exposes this cryptographic hash in the HTTP response JSON.

**Attack Scenario**  
An attacker with read access to the session API endpoint observes the SHA-256 hash of the previous refresh token, aiding in offline verification of token values.

**Impact**  
Exposure of internal session token hashes over the API.

**Recommended Fix**  
Ensure `sanitizeSession` strictly omits `previous_refresh_token_hash`:
```ts
function sanitizeSession(session: DBUserSession): SafeDBUserSession {
    const { session_token_hash, refresh_token_hash, previous_refresh_token_hash, ...safeSession } = session;
    return safeSession as SafeDBUserSession;
}
```

**Priority:** High

### [HIGH] Sensitive 2FA Configuration and Backup Codes Mutated Without Step-Up / Sudo Re-Authentication
**Confidence:** CONFIRMED  
**Category:** Broken Access Control / Account Takeover  
**Affected files:** `src/actions/profile/security-info.actions.ts`, `src/actions/auth/passkey.actions.ts`  
**Affected routes/functions:** `removeTwoFactorMethodAction`, `deletePasskey`, `generateBackupCodesAction`  

**Problem**  
Critical security operations—disabling TOTP 2FA, deleting passkeys, and generating new backup recovery codes—can be invoked by anyone possessing an active session without verifying the account password or performing step-up authentication.

**Attack Scenario**  
If an attacker obtains temporary physical access to a user's browser or exploits an XSS vector, they can immediately invoke `removeTwoFactorMethodAction("totp")` or `deletePasskey()` to disable 2FA, or invoke `generateBackupCodesAction()` to generate and copy 10 new recovery codes, permanently establishing secondary access without knowing the user's password.

**Impact**  
Total bypass and elimination of two-factor authentication safeguards.

**Recommended Fix**  
Require re-entry of the user's current password (or an active 2FA challenge) before executing 2FA removal or backup code regeneration.

**Priority:** High

### [HIGH] Missing Rate Limiting and Attempt Lockout on Recovery Email Code Verification
**Confidence:** CONFIRMED  
**Category:** Brute-Force / Abuse Resistance  
**Affected files:** `src/actions/profile/security-info.actions.ts`  
**Affected routes/functions:** `verifyRecoveryEmailAction` (lines 252–288)  

**Problem**  
In `verifyRecoveryEmailAction`, when a user submits a 6-digit verification code:
```ts
const isValid = await bcrypt.compare(code, tempSession.code_hash);
if (!isValid) return { success: false, error: "Invalid code" };
```
Unlike `resolveCodeVerification` (which increments `failed_attempts` and locks the account after 5 attempts), `verifyRecoveryEmailAction` does not record failed attempts or enforce rate limits.

**Attack Scenario**  
An attacker attempts to verify a recovery email address by repeatedly guessing the 6-digit numeric code within the 10-minute window without encountering lockouts or delays.

**Impact**  
Recovery email hijacking through automated code enumeration.

**Recommended Fix**  
Add `failed_attempts` tracking and account lockout to `verifyRecoveryEmailAction`, matching the controls in `resolveCodeVerification`.

**Priority:** High

## Medium Severity Findings

### [MEDIUM] Proxy Guard Incomplete: Unverified Session Cookie Bypasses Route Protection
**Confidence:** CONFIRMED  
**Category:** Next.js Architecture / Middleware  
**Affected files:** `src/proxy.ts`  
**Affected routes/functions:** `proxy` (lines 26–60)  

**Problem**  
`src/proxy.ts` guards `/profile` routes using:
```ts
const sessionToken = request.cookies.get('session_token')?.value;
if (!sessionToken) { ... }
```
If an unauthenticated client sends an arbitrary cookie `session_token=forged_token`, `!sessionToken` evaluates to `false`. The proxy assumes the user is authenticated and permits the request to pass. While downstream `ProfileLayout` executes `getFullProfile()` which catches invalid sessions, the proxy layer itself is functionally useless as an access control boundary. Furthermore, when `refreshSession` succeeds in `proxy.ts`, response cookies are set on the outgoing response, but request headers forwarded to React Server Components are not updated with the newly minted cookie, triggering race conditions and unwanted redirects.

**Recommended Fix**  
Verify `sessionToken` format or validate tokens in `proxy.ts`, or synchronize cookie state on the forwarded request:
```ts
response.headers.set('Set-Cookie', ...);
request.headers.set('Cookie', ...);
```

**Priority:** Medium

### [MEDIUM] Absence of Admin Role-Based Access Control (RBAC) Architecture
**Confidence:** CONFIRMED  
**Category:** Authorization Architecture  
**Affected files:** `prisma/schema/user.prisma`, `src/actions/`  

**Problem**  
The database schema and application contain no administrative roles (`role`, `isAdmin`, `permissions`). Every user possesses the exact same privileges. There are no admin endpoints, moderation controls, or platform inspection capabilities.

**Impact**  
If administrative capabilities are added in the future, the lack of a standardized authorization layer poses severe vertical privilege escalation risks.

**Recommended Fix**  
Introduce a formal `Role` enum (`USER`, `ADMIN`, `SUPERADMIN`) in `prisma/schema/user.prisma` and implement server-side role assertion guards.

**Priority:** Medium

## Low Severity Findings

### [LOW] Production Database and Cloudflare R2 Credentials in Local Configuration
**Confidence:** CONFIRMED  
**Category:** Secret Management  
**Affected files:** `.env.local`  

**Problem**  
`.env.local` contains live production connection strings (`P_DATABASE_URL` for `cloudburstlab.database.windows.net`) and production Cloudflare R2 API keys (`R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`). Although `.env.local` is gitignored, keeping live production credentials on developer workstations increases the attack surface for credential leakage.

**Recommended Fix**  
Store production credentials strictly in cloud secrets managers (e.g. Azure Key Vault, Cloudflare Secrets, Doppler) and utilize dummy credentials or isolated sandbox instances for local development.

**Priority:** Low

### [LOW] Hardcoded Salt Used for AES-256-GCM Key Derivation
**Confidence:** CONFIRMED  
**Category:** Cryptography  
**Affected files:** `src/lib/encryption.ts` (line 8)  

**Problem**  
`src/lib/encryption.ts` derives symmetric encryption keys using:
```ts
crypto.scryptSync(secret, "clouauth-salt", 32);
```
The salt string `"clouauth-salt"` is static and hardcoded across all deployments.

**Recommended Fix**  
Load a cryptographically random, environment-specific salt from an environment variable (`ENCRYPTION_SALT`).

**Priority:** Low

# Authentication & Authorization Deep Dive

## Admin Authentication
- **Status:** **NOT IMPLEMENTED**
- **Analysis:** The application currently has no admin authentication flow, no admin login endpoint, no admin role definition in Prisma, and no admin route guards. All accounts operate with standard user permissions.
- **Rating:** **Needs Improvement** (Architectural absence)

## General User Authentication
- **Status:** **MEDIUM RISK** (Significantly hardened from Critical)
- **Login Flow:** Users authenticate via username and password (`signIn`), passkeys (`resolvePasskeyVerification`), TOTP (`resolveTotpVerification`), or Google One Tap (`signInWithGoogleOneTap`).
- **Session Flow:** Upon authentication, `createSession` issues an opaque `session_token` (15 min TTL) and a `refresh_token` (30 days TTL if Remember Me, else 15 min). Tokens are hashed with SHA-256 before database storage. Constant-time comparison is enforced and failed token checks no longer terminate sessions.
- **Remaining Vulnerabilities:**
  1. Broken OAuth 2.0 flow permits PKCE bypass and code replay.
  2. 2FA removal requires no password re-entry.
  3. Recovery email verification lacks brute-force lockout.
- **Rating:** **Medium Risk**
